# Mode C Angular 重写评估与实施计划

## 1. 背景

当前 `Mode C` 采用的是“宿主页 + iframe”的集成方式：

- Angular 宿主页位于 `frontend/src/app/pages/mode-c/`
- `cnn-explainer` 以同步后的静态产物运行在 `frontend/public/modules/cnn-explainer/`
- 主项目仅负责外层导航、认证状态和承载 iframe

这套方案已经满足“快速集成”和“低耦合展示”的目标，但它不适合作为长期形态，原因包括：

1. `cnn-explainer` 无法自然复用 `Mode A / Mode B` 的布局、设计令牌和交互规范。
2. iframe 方案难以与 Angular 页面形成统一的状态流、路由语义和组件体系。
3. 样式、无障碍、国际化、埋点和测试都被拆成两层系统，维护成本偏高。
4. 当前同步脚本包含多处构建后补丁，说明子应用并未真正融入平台架构。

因此，下一阶段目标应从“嵌入外部应用”升级为“将 `cnn-explainer` 重写为平台内的 Angular 组件化模块”。

---

## 2. 重写目标

### 功能目标

保留 `cnn-explainer` 的核心能力：

- CNN 结构总览可视化
- 卷积 / ReLU / Pooling / Softmax 等细节解释
- 示例图片切换
- 教学文章与说明区域
- 模型推理结果展示

### 平台目标

重写后应满足：

1. 作为 `Mode C` 原生 Angular 页面运行，不再依赖 iframe。
2. 样式语言与 `Mode A / Mode B` 对齐，不出现明显割裂。
3. 使用主项目已有的：
   - 顶栏体系
   - 认证状态
   - 设计变量
   - 目录结构
   - 构建链路
4. 后续可以逐步接入：
   - 平台统一导航
   - 埋点/日志
   - 主题与响应式规范
   - 更细的无障碍支持

---

## 3. 当前实现评估

### 现状结论

`cnn-explainer` 不是“可直接迁入 Angular 的组件库”，而是“一个独立单页应用”。

### 主要技术特点

1. 技术栈为 `Svelte + Rollup + D3 + TensorFlow.js`，与主项目 Angular 技术栈不同。
2. 入口按独立站点设计，默认接管整页。
3. 依赖静态 `index.html` 注入全局脚本。
4. 大量逻辑依赖全局 DOM 查询、全局样式和全局脚本加载顺序。
5. 页面结构并非按“组件可复用”原则拆分，而是按“教学应用页面”组织。

### 结论

这不是一次“简单迁移”，而是一次“有保留地重构”：

- 数据模型和交互思想可以保留
- 代码结构、渲染层、状态层和样式层应重新落到 Angular 体系

---

## 4. 重写范围评估

### 建议保留的内容

以下内容适合“迁移思路 / 迁移数据”，而不是直接照搬：

1. CNN 可视化的数据结构设计
2. 模型层级概念与教学交互逻辑
3. 示例图片、模型资源、说明文案
4. 细节面板的内容分层方式

### 建议重写的内容

以下内容建议按 Angular 体系重做：

1. 页面入口与路由挂载
2. 状态管理
3. DOM 事件处理
4. 视图组件拆分
5. 样式系统
6. 顶栏、按钮、卡片、布局容器
7. 资源加载与模型初始化流程

### 风险点

1. D3 交互逻辑迁移复杂，初期容易出现行为回退。
2. `cnn-explainer` 教学细节丰富，若一次性重写全部内容，周期会过长。
3. 若追求完全 1:1 复刻，工程复杂度会显著上升。

### 建议策略

不要一次性“全量复刻”。  
建议采用“先可用、再精细、最后补齐”的三阶段重构策略。

---

## 5. 推荐实施策略

### 总体策略

采用 **分阶段替换**：

1. 先保留现有 iframe 版作为可运行基线
2. 新建 Angular 原生 `Mode C` 功能分支实现
3. 按功能块逐步替换
4. 当 Angular 版达到验收线后，再移除 iframe 版

### 为什么不建议一次性替换

1. 你当前项目已有可演示结果，不能让 `Mode C` 在重构期间完全不可用。
2. `cnn-explainer` 包含大量教学交互，适合拆块验证。
3. 分阶段能更好地控制视觉对齐和行为一致性。

## 7. 各阶段详细任务

### Phase 0：需求冻结与资产盘点

目标：明确“必须保留什么，不必 1:1 保留什么”。

任务：

1. 盘点 `cnn-explainer` 当前功能模块
2. 给功能分级：
   - P0：必须保留
   - P1：建议保留
   - P2：可延期
3. 盘点资源：
   - 图片
   - 模型
   - 字体
   - 说明文案
4. 建立视觉对齐参考：
   - 顶栏
   - 按钮
   - 卡片
   - 表单
   - 状态标签

交付物：

- 功能清单
- 资源清单
- UI 对齐基线

### Phase 1：Angular 原生骨架

目标：在不依赖 iframe 的前提下，建立一个平台内可运行的 `Mode C` 页面骨架。

任务：

1. 新建 `Mode C` 原生模块目录，建议放在：
   - `frontend/src/app/pages/mode-c/`
   - `frontend/src/app/features/mode-c-explainer/`
2. 建立基础组件结构：
   - `mode-c-shell`
   - `mode-c-overview`
   - `mode-c-detail-panel`
   - `mode-c-article`
3. 抽出资源加载服务：
   - 模型加载
   - 示例图加载
   - 静态配置加载
4. 将当前顶部认证区与 `Mode A / B` 风格完全统一

交付物：

- 可访问的 Angular 原生 `Mode C` 页面
- 不再依赖 iframe 的空骨架

### Phase 2：Overview 主视图重写

目标：先拿下“最核心、最可见”的网络总览。

任务：

1. 将 `cnn-explainer` 的网络图数据结构迁入 Angular
2. 建立 `Mode C` 的状态服务
3. 用 Angular + D3 或 Angular + SVG 重写：
   - 网络层节点
   - 连线
   - hover 高亮
   - click 选中
4. 保留当前最重要的交互闭环：
   - 切换示例图
   - 触发模型推理
   - 高亮当前层

交付物：

- 可操作的主网络图

### Phase 3：Detail View 体系

目标：逐个恢复教学解释的深度内容。

任务：

1. 拆成独立 Angular 组件：
   - `conv-detail`
   - `relu-detail`
   - `pool-detail`
   - `softmax-detail`
2. 将交互控制从全局 DOM 迁移到组件输入输出
3. 建立统一 detail panel 切换机制

交付物：

- 细节解释面板系统

### Phase 4：文章区与教学内容迁移

目标：恢复 `cnn-explainer` 作为教学模块的完整性。

任务：

1. 将文章内容拆为 Angular 模板或结构化数据
2. 将图片和公式资源迁入主项目静态资源目录
3. 清理视频教程与外链依赖
4. 让说明区与上方交互视图在信息架构上保持一致

交付物：

- 原生文章说明区

### Phase 5：视觉对齐与体验打磨

目标：让 `Mode C` 看起来像 DeepVision Studio 的原生模块，而不是移植页面。

任务：

1. 对齐 `Mode A / B` 的：
   - 顶栏样式
   - 卡片阴影
   - 边框半径
   - 字号层级
   - 按钮体系
2. 统一色板与状态色
3. 做响应式适配
4. 补键盘导航和基础无障碍

交付物：

- 视觉统一的 `Mode C`

### Phase 6：验收与切换

目标：将新版本正式替换旧版 iframe。

任务：

1. 建立验收清单
2. 对照旧版逐项回归
3. 移除 `iframe` 入口
4. 下线同步脚本和静态嵌入目录的强依赖

交付物：

- 原生 Angular 版 `Mode C`
- 旧方案归档说明

## 8. 目录重构建议

建议新增结构如下：

```text
frontend/src/app/features/mode-c-explainer/
  components/
    overview/
    detail-panels/
    article/
    shared/
  services/
    mode-c-model.service.ts
    mode-c-state.service.ts
    mode-c-assets.service.ts
  models/
    mode-c.types.ts
  utils/
    mode-c-d3.ts
    mode-c-math.ts
```

说明：

- `pages/mode-c/` 只负责宿主页面
- 核心教学逻辑应进入 `features/mode-c-explainer/`
- 这样后续维护方式会更接近 `Mode A / B`

## 9. 技术路线建议

### 渲染层建议

优先考虑：

1. Angular 组件 + SVG + 少量 D3

原因：

- 更容易纳入 Angular 生命周期
- 更容易做输入输出控制
- 更容易测试
- 比“整页依赖 D3 操作 DOM”更可维护

不建议：

1. 把现有 Svelte 编译产物继续往 Angular 里硬包
2. 在 Angular 中大面积保留原有全局 DOM 操作代码

### 状态管理建议

`Mode C` 建议单独使用一个本地状态服务，不必一开始就引入复杂状态框架。

建议状态拆分：

- 当前输入图片
- 模型结构
- 当前选中层
- 当前 detail panel
- 可视化 hover 状态
- 文章联动状态

## 10. 资源迁移建议

建议将 `cnn-explainer` 的静态资源重新整理到主项目资源目录，例如：

```text
frontend/public/mode-c/
  assets/
    img/
    figures/
    fonts/
    data/
```

说明：

- 不建议继续放在 `modules/cnn-explainer/`
- 那个目录更像“旧嵌入方案遗产目录”
- 重写后应转为主项目自己的资源布局

## 11. 验收标准

### 功能验收

1. 不再使用 iframe
2. 页面能加载模型和示例图
3. 网络总览可交互
4. 至少支持 4 类 detail view：
   - Convolution
   - ReLU
   - Pooling
   - Softmax
5. 保留说明文章区

### 视觉验收

1. 顶栏与 `Mode A / B` 风格统一
2. 卡片、按钮、输入控件风格统一
3. 页面不再像“外部嵌入应用”

### 工程验收

1. 无需同步脚本才能运行 `Mode C`
2. 无需外部独立仓库即可启动
3. 资源路径纳入 Angular 主项目

---

## 12. 最终建议

### 建议结论

这项工作 **值得做**，但应按“重构项目”而不是“样式迁移任务”来排期。

### 推荐执行方式

1. 先把目标定为“Angular 原生版 `Mode C` MVP”
2. 第一阶段只完成：
   - 原生页面骨架
   - 顶栏对齐
   - Overview 主视图
   - 基础 detail panel
3. 文章区和高复杂度细节放第二阶段补齐

### 是否建议立即开始

建议开始，但前提是：

1. 先接受“不会一次性 100% 复刻”
2. 允许按阶段交付
3. 允许保留少量旧版作为对照基线直到新版本稳定
